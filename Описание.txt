ТДМ — Order Execution Models

Назначение документа

Данный документ описывает бизнес-процесс исполнения заказа в ТДМ без привязки к UI, API, БД, FSM и технической реализации.

Цель документа — сформировать единое доменное понимание жизненного цикла заказа для последующего построения:

- Order Lifecycle
- Order FSM
- FSM клиента
- FSM водителя
- бизнес-правил обработки заказа

---

1. Общие участники процесса

Клиент

Клиент:

- создает заказ;
- определяет параметры поездки;
- участвует в выборе исполнителя в зависимости от модели исполнения;
- подтверждает факт посадки;
- может отменить заказ.

---

Водитель

Водитель:

- получает информацию о доступных заказах;
- может откликаться на заказ;
- может стать кандидатом или исполнителем;
- участвует в Boarding Verification;
- выполняет поездку.

---

Система ТДМ

Система:

- управляет жизненным циклом заказа;
- формирует пул видимости;
- отслеживает время жизни заказа;
- фиксирует события;
- управляет Boarding Verification;
- регистрирует результат поездки.

---

Внешний водитель

В модели VOTE фактическая перевозка может быть выполнена водителем, который не является участником заказа в системе ТДМ.

Такой водитель участвует только в фактическом выполнении перевозки и не является  участником заказа в сервисе. Заказ выполняемый внешним водителем отменяется клиентом или заканчивается по таймеру.

---

2. Общие доменные понятия

PoolVisibility

Набор водителей, которым в данный момент доступен заказ.

Состав может изменяться во времени.

---

CandidatePool

Набор водителей, откликнувшихся на заказ.

Состав зависит от модели исполнения.

---

AssignedDriver

Водитель, выбранный исполнителем заказа, или сам взявший заказ в Direct заказе .

---

BoardingVerification

Доменный процесс подтверждения фактической встречи клиента и водителя.

Без успешного завершения Boarding Verification поездка не может считаться начавшейся.

---

ActualCarrier

Фактический перевозчик клиента.

В большинстве случаев совпадает с AssignedDriver.

В модели VOTE может отличаться, если не было выбора кандидата.

---

OrderExpiration

Момент утраты актуальности заказа.

После наступления этого момента заказ не может получить исполнителя.

---

3. Модель DIRECT

Бизнес-смысл

Клиент ищет первого доступного водителя.

Исполнитель определяется по принципу:

«Кто первый принял заказ — тот и выполняет его.»

---

Участники

- Клиент
- Водители из PoolVisibility
- Система

---

Этапы исполнения

1. Публикация заказа

Заказ становится доступен пулу видимости.

2. Захват заказа

Один из водителей принимает заказ.

В момент принятия:

- водитель становится AssignedDriver;
- поиск исполнителя завершается.

3. Сближение

Клиент и водитель движутся к месту встречи.

4. Boarding Verification

Подтверждается кнопкой в интерфейсе водителя  фактическая встреча клиента и водителя.

5. Выполнение поездки

Осуществляется перевозка пассажира.

6. Завершение

Поездка успешно завершена.

FSM заказа ТДМ (Order Lifecycle State Machine)
1. Общий принцип

FSM разделяется на 3 уровня:

Order Lifecycle FSM — жизненный цикл заказа
Driver Matching FSM — подмодель внутри поиска исполнителя
Boarding / Ride FSM — старт и выполнение поездки

Order — верхнеуровневая машина, остальные встроены как подсостояния.

2. Состояния заказа (Order States)
2.1. INIT / DRAFT (опционально)

Заказ формируется.

Переходы:

→ CREATED
2.2. CREATED

Заказ создан, все данные зафиксированы.

Условия входа:

заполнены маршрут, тип, класс, требования, способ подачи

Переходы:

→ MATCHING_STARTED
→ CANCELLED
→ EXPIRED (если NOW + таймер истёк)
2.3. MATCHING_STARTED

Активирован Driver Matching.

Внутри активируется:

CandidatePool
стратегия VOTE / OFFER / DIRECT

CREATED
  ↓
MATCHING_STARTED

  ├─ VOTE → candidates → selected → boarding → ride
  ├─ OFFER → offers → selected → assigned → ride
  └─ DIRECT → assigned → ride

9. Важное архитектурное следствие
Vote / Offer / Direct — не состояния заказа
это режимы одной подсистемы Matching
“список проголосовавших” не существует
есть only candidateDrivers[]
FSM не хранит UI-смысловые сущности
только бизнес-переходы

Правильный процесс миграции

Это несколько шагов, не один.

Шаг 1. Reverse mapping (код → предполагаемая FSM)

Берёшь WhatsApp-код и отвечаешь:

Какие состояния он ИМИТИРУЕТ?
Какие события он обрабатывает?
Где у него скрытые переходы?

Важно: это ещё не “истинная FSM”, а реконструкция.

Шаг 2. Сопоставление с уже построенной FSM ТДМ

Дальше ты делаешь матчинг:

кодовое состояние → доменное состояние FSM

И находишь:

где код упрощает FSM
где код пропускает состояния
где код объединяет несколько состояний в одно
Шаг 3. Gap analysis (разрывы модели)

Обычно всплывает:

- отсутствующие события
- недостающие таймеры
- неучтённые переходы (EXPIRED, CANCELLED, BOARDING)
- смешанные бизнес-режимы (DIRECT/VOTE/OFFER)
Шаг 4. Адаптация бота к FSM (не наоборот)

Только теперь:

бот переписывается под FSM,
а не FSM под бот
Шаг 5. Введение event-driven слоя (желательно)

Чтобы дальше не повторять проблему:

WhatsApp → emits events → FSM engine → state transitions
Ключевая мысль

FSM уже построенная у тебя — это:

“истинная модель домена”

Код WhatsApp:

“частичная историческая реализация”

Они не обязаны совпадать.

Ответ на твой вопрос напрямую

Можно ли сразу переключить код WhatsApp на FSM?

Нет.

Это всегда:

миграция в 3–5 шагов:
1. восстановление текущего поведения
2. сопоставление с FSM
3. выявление разрывов
4. постепенный рефакторинг
5. только потом переключение на FSM как источник истины

Если хочешь следующий логичный шаг — можно разобрать:

как именно разложить текущий WhatsApp flow на события FSM (event extraction)

Это самый критичный этап, там обычно находится 70% несоответствий.
